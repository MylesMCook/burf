Agents in Berth can drive each other, and so can you, a hook, a flow or a
plugin. Four pieces on every box do it, the same from the app, the CLI and
the API:

| Piece | CLI | Box API |
| --- | --- | --- |
| Start work: a worktree with an agent in it | `berth task new BOX/LOC/NAME --agent claude --prompt …` | `POST /v1/tasks` |
| Prompt a running agent | `berth session send BOX/SESSION TEXT` | `POST /v1/sessions/{name}/send` |
| Wait for its turn to end | `berth session wait BOX/SESSION --turn ID` | `GET /v1/turns/{id}/wait` |
| Run a check where it works | `berth exec BOX/LOC[/WT] -- COMMAND` | `POST /v1/exec` |

On a box, `berthd` takes the same commands without the `BOX/` prefix, which
is what agents there use.

The patterns below (loop, review, hand-off, broadcast, try several ways) are
[durable runs](/guides/runs) on boxes that have them: the box executes them
and keeps a journal, so they keep going while the laptop sleeps and resume
after `berthd` restarts.

## Send

```sh
berth session send devl/shop-checkout-claude "Rebase on main and fix any conflicts"
# Sent to shop-checkout-claude (turn shop-checkout-claude#4)
```

The text is pasted as one block (so a multi-line prompt is one prompt), then
Enter is pressed (`--no-enter` leaves it typed). Prompts never appear in
events or logs; only `session.sent` with the session's name.
`before:session.send` hooks can refuse a prompt.

A send returns the **turn** it started (see
[turns](/concepts/sessions-and-agents#turns)), the journal number of the
send (`seq`) and the box's time (`at`); `--json` prints them:

```json
{ "sent": true, "turn": "shop-checkout-claude#4", "seq": 812, "at": "2026-10-04T09:12:03.411Z" }
```

| Option | API field | Effect |
| --- | --- | --- |
| `--when now` (default) | `when: "now"` | Type it at once. Refused (HTTP 409) while the agent is `waiting` for you |
| `--when idle` | `when: "idle"` | Hold it in the box's inbox for the session (up to 16 prompts) and type it once the agent is idle or finished; the turn is `queued` until then. Never typed while the agent waits for you |
| `--force` | `force: true` | Type it even into an agent waiting for you. For people answering it, never for agents and scripts |
| `--idem KEY` | `idem_key` | A retry with the same key returns the turn it already made (`duplicate: true`) and types nothing |

A request without `when` (an older client) types at once, as before. With
`--wait`, it then waits for that turn to end (up to `--timeout`, 30 minutes
by default). With `--queue`, a prompt for a box that cannot be reached waits
on the laptop instead of failing; see [the offline queue](/guides/offline-queue).

## Wait

```sh
berth session wait devl/shop-checkout-claude --turn 'shop-checkout-claude#4'   # that turn
berth session wait devl/shop-checkout-claude                                    # finished or waiting, now or later
berth session wait devl/shop-checkout-claude --for finished --timeout 1h
berth session turns devl/shop-checkout-claude                                   # its last turns
```

A turn wait returns when the turn ends (`finished`, `exited`, `lost`) or
waits for you (`waiting`), so a prompt sent while the agent was mid-turn is
not ended by the turn it was already in. It needs no clock: the box orders
everything by its journal. `GET /v1/turns/{id}/wait?until=end|waiting&timeout=90s`
is the API (encode `#` as `%23`).

`berth session wait` without `--turn` returns when the agent is `finished`
or `waiting` (or the states you ask for), including right now, or when its
program exits. Over the API, `GET /v1/sessions/{name}/wait?after=` still
works for older clients: the box places `after` in its journal's order, so a
caller whose clock runs ahead or behind the box's still sees the turn end.
A wait that times out reports the last state it saw.

## Exec

```sh
berth exec devl/shop/checkout -- pnpm test --changed
```

Runs a command to completion through a login shell in the location or
worktree, with its environment, and returns its exit code and the last 64 KB
of output (`--timeout`, 10 minutes by default). `before:exec` hooks can
refuse it. With `--detach` (API `detach: true`) it answers at once with a
run whose result holds the exit code and output (`berth run get`), so no
caller blocks on a long check.

## Patterns

### Loop until a check passes

```sh
berth loop devl/shop-checkout-claude --check "pnpm test" --prompt "Make the tests pass" --max 5
```

It prompts, waits for that prompt's turn, runs the check in the session's
worktree, and sends back what failed until the check passes or `--max`
rounds (default 5) run out. What goes back is short, since the agent reads
every byte of it: the lines that say what failed and the end of the output,
without colours, at most about 3 KB, never the whole log. Each round's
prompt carries an idempotency key, so a retried send never types it twice.
It stops if the agent is waiting for a human (the box refuses to type into
it); `--turn-timeout` bounds each turn. On a box with runs it is a run of
the `loop` template on the box: Ctrl-C stops following it, not the loop
(`--cancel-on-exit` cancels it, `--detach` only starts it), and it survives
the laptop sleeping and `berthd` restarting. In the app, **Loop until…** in
a session's menu does the same, and running loops show in a panel in the
corner, from every device.

### Hand off

A new worktree and agent picking up where another left off, with a
**handoff packet**:

```sh
berth run start devl --template handoff --param session=shop-checkout-claude \
  --param name=checkout-tests --param agent=codex --param prompt='Write the missing tests.'
```

The source agent is asked to write `.berth/handoff/<run>.md` (Done, Left,
Decisions, Gotchas; at most 30 lines). Berth adds the diffstat, the commits,
the last check's failing tail and the turn log, caps it at about 2 KB, and
carries uncommitted work over. The new agent's first prompt only points at
the file. With `--param native=true` and the same vendor on the same box,
the new agent continues the source's own conversation instead
(`claude --resume <id> --fork-session`, `codex resume <id>`). The app's
**Hand off to…** with **In a new worktree** does this; without a runs box it
starts the task with a prompt that names where the work was.

### Review

A second agent reviewing a worktree, with its own session identity so its
turns never end the author's waits:

```sh
berth run start devl --template review --param session=shop-checkout-claude --param send_back=true
```

By default the reviewer is a [headless agent](/guides/runs#headless-agents)
that can only read; its verdict (at most 15 lines) is the run's output, and
`send_back` sends it to the author. The app's **Review with…** starts an
interactive reviewer beside the author.

### Broadcast

The app can send one prompt to several agents at once, from the composer's
**Running agents** tab: pick the running agents it goes to, write the prompt
or start from a saved one, and read or change each agent's copy under
**Options**. **Send a prompt to several agents…** in ⌘K, **Send to N
agents…** on the Agent Dashboard, **Prompt agents…** on a selection in
Worktrees and **Send to several…** in the prompt library open it with those
agents picked; a session's **Send prompt…** and **Loop until…** open it on
that one (a loop prompts, waits, runs the check and sends failures back). The prompt's `{{variables}}` are filled in for each agent
(its branch, worktree, project, box), sends go one after another, and you
can wait for every turn to end and read what each said. An agent that is
waiting for you is skipped, never typed into. Agents on offline boxes can be
queued for when they're back. On boxes with runs, each box's share is a
`broadcast` run there: the box holds each prompt until its agent is idle
and waits for every turn, even if the app quits.

### Try several ways

**Try N ways…** (⌘K, or a session's Orchestrate menu), or picking several
agents in the composer, gives one task to several agents, each in its own
worktree, verifies them with a check, has a
headless judge rank them, and lets you pick in Review's **Compare**. See
[attempts](/guides/runs#attempts).

### Chain with hooks and flows

A hook on the box can start the next step when an agent finishes. Here a
Codex session named `reviewer` looks at whatever Claude Code just did; the
`case` keeps the reviewer's own finished turns from prompting it again:

```json title="~/.berth/hooks.json"
{
  "hooks": [
    { "on": "agent.finished", "run": "case \"$BERTH_AGENT\" in claude) berthd session send reviewer \"Review what changed in $BERTH_PATH\";; esac" }
  ]
}
```

For anything with more than one step (run the tests, send failures back,
notify you), use a [flow](/guides/automations).

## From an agent

The skills Berth installs (`berthd integrations install claude`) teach
agents these commands, so an agent can split work across worktrees, ask
another agent for a review, or loop on a check by itself. The
`berth-orchestrate` skill also tells them never to answer another agent's
question on the user's behalf. See [agent integrations](/guides/agent-integrations).
The same install adds `berthd mcp`, an MCP server of typed, non-blocking
tools for the same things; see [runs](/guides/runs#from-an-agent-mcp).

## From a plugin

Plugins get the same operations as `berth.orchestrate`: `send` (which
resolves with the turn), `waitTurn`, `wait`, `exec`, `handoff`, `review` and
`loop` (runs on boxes that have them), and `runs` to start, follow, decide
and cancel any run; see
[the plugin SDK](/reference/plugin-sdk#orchestrate).

## Agent state

All of this relies on agents reporting their turns: fully through hooks for
Claude Code, Codex (with its hooks trusted), Gemini CLI and OpenCode, Cursor
except for "needs you", and by reading the terminal for anything else. See
[sessions and agents](/concepts/sessions-and-agents#turns).

## Agents driving agents, cheaply

An orchestrating agent pays in tokens for everything it reads, and so does
every agent it prompts. Berth keeps both small: waits are event-driven (wait
on the turn; never poll `session screen` or rerun `sessions`), `--json`
output is compact, prompts Berth writes (loop feedback, GitHub comments in
flows, handoff packets, the judge's summaries) are short and capped, and
idempotency keys mean a resumed caller never sends the same prompt twice.
Each [template's budget](/guides/runs#templates) is in its description
(`berth run templates`). An agent's shell tool usually times out within
minutes, so the skill tells agents to wait in short steps
(`session wait --turn ID --timeout 90s`, repeated) or in the background.
