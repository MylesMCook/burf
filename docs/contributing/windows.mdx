---
title: Windows client
description: Building and checking the native Windows desktop and command-line client.
---

Berth on Windows x64 connects to already-running Linux and macOS boxes. The first Windows release includes the desktop app and `berth.exe` client. Windows cannot be a box. Install and start `berthd` on a Unix box, then paste its pairing link into Berth or use `berth pair`. Remote terminals, agents, previews, files, and port forwards run through the local client.

## SSH provisioning and editors

`berth add ssh` and GUI SSH installation are unavailable from Windows. Setup currently requires OpenSSH connection multiplexing and background execution, which native Windows OpenSSH [does not support](https://github.com/PowerShell/Win32-OpenSSH/wiki/Project-Scope). The CLI refuses before inspecting SSH keys, changing known hosts, or connecting to a box.

On Windows, the editor connection files generated by `berth ssh-config` target native Windows OpenSSH. Select that SSH client in your editor when another `ssh.exe` precedes it on PATH. Git/MSYS/Cygwin SSH clients are outside this release's supported scope for those generated files.

Editors found only through a `.cmd` or `.bat` launcher open remote folders through their registered URL scheme. File-at-line navigation requires a native `.exe` command line tool; batch-only launchers do not provide it.

## Build

Use the repository's existing Go and pnpm versions, Rust's `x86_64-pc-windows-msvc` target, Visual Studio C++ build tools, and WebView2. These are prerequisites, not installed by the build script. Restore the locked app dependencies with `pnpm install --frozen-lockfile` in `app`.

Build the pinned Linux tmux helpers on a Docker host with `scripts/build-tmux.sh bin amd64 arm64`, then copy `bin/tmux-linux-amd64` and `bin/tmux-linux-arm64` into the Windows checkout. The Windows script builds the matching Linux daemon helpers itself. It does not build a Windows daemon.

```powershell
./scripts/windows-build.ps1 -Version 0.3.9
# Only stage Go resources for a native Rust build:
./scripts/windows-build.ps1 -Version 0.3.9 -StageOnly
```

`make app-build-windows` invokes the same script. `make app-build APP_TARGET=x86_64-pc-windows-msvc` selects it too. A debug app finds only `bin/berth.exe` after its explicit development override and bundled copy. A release app executes only its adjacent `berth-cli.exe`; it never finds an agent executable on PATH. The terminal command lives separately at `cli/berth.exe`, avoiding a case-insensitive collision with the app's `Berth.exe`.

The script writes `dist/windows/Berth-windows-x64-setup.exe`, `berth-windows-amd64.zip`, and `windows-checksums.txt`. The CLI archive includes the Linux daemon and tmux helpers used when upgrading remote boxes. It contains no Windows daemon.

## Install and update

NSIS installs for the current user without elevation. Installation does not change PATH or register a login task. The app's **Start at login** checkbox explicitly enables the per-user login task. Settings > General > Command line explicitly adds the `cli` folder to the user's PATH, with a removal control. Uninstall removes only Berth's owned PATH entry and login task. Agent keys and paired-box state remain in the user's Berth config directory.

The installer checks both bundled CLI candidates and stops only a process owned by one of them with `berth agent stop --drain`. That command waits for the process to exit; a timeout cancels installation instead of killing it. A failed installation restores the old client executables and starts the previously running client again. Remote sessions remain on their boxes. Recovery belongs to the installer because the Windows updater exits the app after launching it.

Both a normal higher-version installer and the in-app updater replace files in place, preserving explicit PATH and login consent. The build script obtains the exact locked Tauri CLI's NSIS template, verifies its pinned SHA256, and generates a small maintenance-page patch in the ignored `binaries` directory. No copy of the full template is maintained in the repository. A CLI update requires reviewing that patch and its pinned template version. PATH integration uses a command embedded in the app, and uninstall runs the old app's headless cleanup mode. No unsigned PowerShell script file is executed and no execution-policy setting changes.

Only the maintainer's `v*` tag release job receives the existing `TAURI_SIGNING_PRIVATE_KEY`. Pass `-Release` to make a signed updater artifact. Windows uses `latest-windows.json` and the `windows-x86_64` platform key. macOS keeps `latest.json`. The Tauri updater signature authenticates updates; this release does not require or create an Authenticode certificate. Windows may show its standard unsigned-app warning.

## Verify

```powershell
go test ./internal/service ./internal/agent ./cmd/berth
cargo test --locked --manifest-path app/src-tauri/Cargo.toml --lib
cd app
node --experimental-strip-types --test src/lib/platform.test.ts
pnpm exec playwright test e2e/windows-client.spec.ts
```

From the repository root, `node --test scripts/windows-installer-template.test.mjs scripts/windows-packaging.test.mjs` checks the upgrade patch and ownership/recovery wiring. On Windows it also runs the embedded read-only PATH query and pure PATH transformations under the existing PowerShell policy. These tests do not edit PATH or register tasks.

Use a fresh `BERTH_HOME` and separate client ports for native tests. Do not point synthetic checks at a personal running agent. Local client hooks use PowerShell syntax on Windows; Berth does not translate POSIX shell commands. Commands executed on Unix boxes still use the box's shell.

Long Windows state paths keep their data in place and use a stable, private socket under the user's local cache `berth-ipc` directory. Ordinary state paths retain their in-directory socket.

The Windows CI job compiles Rust, runs native Go tests, and builds an unsigned installer without release secrets. Browser tests exercise Windows shortcut labels and capability-based onboarding with isolated fixtures. A maintainer must still check the native window, WebView2 child panes, terminal clipboard, pairing with a real Unix box, opt-in login startup, installed CLI lookup, upgrade with an active agent, failed upgrade recovery, and ownership-safe uninstall on Windows. Compilation and fixtures do not establish those native GUI outcomes.

## Manual installer acceptance

After explicit approval for a Windows host, use `scripts/test-windows-install.ps1 -Installer <first.exe> -UpgradeInstaller <higher-version.exe>`. This is never run by CI. It refuses elevation and existing product, URL-scheme, PATH-owner, or shortcut registrations before installation. WebView2 must already be present.

The runner creates a unique folder under Documents/Codex and uses a synthetic `BERTH_HOME`, user directory, and loopback ports. It checks fresh-install consent, private API startup, a login task owned by `cli/berth.exe`, literal isolated task environment, an explicitly added PATH entry, manual higher-version upgrade, clean stop beyond the crash-retry interval, and supported uninstall. It compares the final task set and exact user PATH with their baselines, verifies personal preview pairing/identity files are unchanged, and retains synthetic keys and local evidence for inspection. It does not test failed-upgrade rollback without a separately prepared artifact and assertions.
