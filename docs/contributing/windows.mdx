---
title: Windows client
description: Building and checking the native Windows desktop and command-line client.
---

Burf's Windows source preview targets x64 and ARM64. It includes the Go/Wails
desktop app and `burf.exe` client with a `berth.exe` alias. The client can run
installed local agent CLIs and connect to already-running Linux or macOS boxes;
Windows has no box daemon. Install and start `berthd` on a Unix box, then paste
its pairing link into Burf or use `burf pair`. Remote terminals, agents,
previews, files and port forwards run through the local client. Signed Windows
downloads and an application update feed remain unavailable.

## SSH provisioning and editors

`burf add ssh` and GUI SSH installation are unavailable from Windows. Setup currently requires OpenSSH connection multiplexing and background execution, which native Windows OpenSSH [does not support](https://github.com/PowerShell/Win32-OpenSSH/wiki/Project-Scope). The CLI refuses before inspecting SSH keys, changing known hosts, or connecting to a box.

On Windows, the editor connection files generated by `burf ssh-config` target native Windows OpenSSH. Select that SSH client in your editor when another `ssh.exe` precedes it on PATH. Git/MSYS/Cygwin SSH clients are outside this release's supported scope for those generated files.

Editors found only through a `.cmd` or `.bat` launcher open remote folders through their registered URL scheme. File-at-line navigation requires a native `.exe` command line tool; batch-only launchers do not provide it.

## Build

Use Go 1.27, Node 22 and the repository's pnpm lockfile. The desktop module and
frontend runtime pin Wails v3 `3.0.0-beta.28`, a prerelease. Rust is not part of
the build. Native execution needs Windows 10 or 11 with the Microsoft WebView2
Evergreen Runtime already installed. Creating an installer also needs an
existing NSIS `makensis.exe`; `NSIS_COMPILER` may name its absolute path.
The script does not install these prerequisites or change machine policy.
Restore frontend dependencies with `pnpm install --frozen-lockfile` in `app`.

Build the pinned Linux tmux helpers on a Docker host with `scripts/build-tmux.sh bin amd64 arm64`, then copy `bin/tmux-linux-amd64` and `bin/tmux-linux-arm64` into the Windows checkout. The Windows script builds the matching Linux daemon helpers itself. It does not build a Windows daemon.

```powershell
./scripts/windows-build.ps1 -Architecture amd64
# Build the Go app and ZIPs without compiling an NSIS installer:
./scripts/windows-build.ps1 -Architecture amd64 -StageOnly
# ARM64 uses the same pinned runtime and matching loader:
./scripts/windows-build.ps1 -Architecture arm64 -StageOnly
```

`make app-build-windows` invokes the same script on Windows, as does
`make app-build APP_GOOS=windows APP_GOARCH=amd64`. A native app compiled with
the Go `dev` tag checks its absolute `BERTH_CLI` override, bundled CLI, then
the repository's `bin/burf.exe`. Packaged apps execute only their adjacent
`berth-cli.exe`; they never find an agent executable on PATH. Terminal commands
live separately at `cli/burf.exe` and the compatible `cli/berth.exe`, avoiding
a case-insensitive collision with the app's `Burf.exe`.

The app folder is `dist/native/windows-amd64/` or `windows-arm64/`. Archives
and optional installers are in `dist/windows/`, including
`Burf-windows-x64.zip`, `Burf-windows-x64-setup.exe`,
`burf-windows-amd64.zip` and `windows-checksums.txt`; ARM64 uses the matching
architecture names. The CLI archive includes Linux daemon helpers and any
staged tmux helpers used to upgrade remote boxes. It contains no Windows daemon.

The raw browsing child uses the loader from Microsoft.Web.WebView2 SDK
`1.0.4258.31`. Package and loader SHA256 digests are pinned, and the Windows
build requires its Microsoft Authenticode signature to validate before staging.
`WEBVIEW2_SDK_PACKAGE` may point to the exact cached NuGet archive. Its license
and notice ship beside the loader. A matching hash or cross-build alone does
not prove native execution or Windows certificate-chain trust.

## Install and update

The application updater remains disabled while the fork has no signed release
feed. The installer behavior below also applies to an intentional local
installer upgrade; it does not establish an enabled feed.

NSIS installs for the current user without elevation. Installation does not change PATH or register a login task. The app's **Start at login** checkbox explicitly enables the per-user login task. Settings > General > Command line explicitly adds the `cli` folder to the user's PATH, with a removal control. Uninstall removes only Burf's owned PATH entry and login task. Agent keys and paired-box state remain in the user's Burf config directory.

The installer checks both bundled CLI candidates and stops only a process owned by one of them with `burf agent stop --drain`. That command waits for the process to exit; a timeout cancels installation instead of killing it. A failed installation restores the old client executables and starts the previously running client again. Remote sessions remain on their boxes.

An intentional higher-version installer replaces files in place and preserves
explicit PATH and login consent. The project-owned NSIS template and recovery
hooks live in `scripts/windows`; they do not depend on a downloaded bundler
template. PATH integration uses the reviewed PowerShell command embedded in
the Go app, and uninstall uses the app's headless cleanup mode. No unsigned
PowerShell script file is executed and no execution-policy setting changes.

`-Release` currently refuses because no approved Windows signing and
publication workflow exists. No upstream signing identity or feed is adopted.
Local app builds do not create an Authenticode certificate; Windows may show
its standard unsigned-app warning. This is separate from the mandatory
Microsoft signature check on the WebView2 loader.

## Verify

```powershell
go test ./internal/service ./internal/agent ./cmd/burf
node scripts/native-prepare.mjs bindings
Push-Location app/native
go test ./desktop ./nativebrowser
Pop-Location
cd app
node --experimental-strip-types --test src/lib/platform.test.ts
pnpm exec playwright test e2e/windows-client.spec.ts
```

From the repository root, `node --test scripts/windows-installer-template.test.mjs scripts/windows-packaging.test.mjs` checks the upgrade patch and ownership/recovery wiring. On Windows it also runs the embedded read-only PATH query and pure PATH transformations under the existing PowerShell policy. These tests do not edit PATH or register tasks.

Use a fresh `BERTH_HOME` and separate client ports for native tests. Do not point synthetic checks at a personal running agent. Local client hooks use PowerShell syntax on Windows; Burf does not translate POSIX shell commands. Commands executed on Unix boxes still use the box's shell.

With explicit approval on a disposable Windows host, run the focused task-registration check from a non-administrator terminal:

```powershell
$env:BERTH_TEST_WINDOWS_TASK = '1'
try { go test ./internal/service -run '^TestWindowsTaskRegistrationAsOrdinaryUser$' -v }
finally { Remove-Item Env:BERTH_TEST_WINDOWS_TASK }
```

It creates, runs and removes one uniquely named task with synthetic state. Normal test runs skip it. Passing XML validation or running tests as administrator does not prove that ordinary-user task registration works. A registration denial must be investigated without disabling endpoint protection or changing machine policy.

Long Windows state paths keep their data in place and use a stable, private socket under the user's local cache `berth-ipc` directory. Ordinary state paths retain their in-directory socket.

The Windows CI job builds the Go/Wails app, runs native Go tests and builds an
unsigned installer without release secrets. Browser tests exercise Windows
shortcut labels and capability-based onboarding with isolated fixtures. A
maintainer must still check the native window, WebView2 children, terminal
clipboard, real pairing, opt-in login startup, installed CLI lookup, active
agent upgrade, failure recovery and ownership-safe uninstall on Windows.
Compilation and fixtures do not establish those native outcomes.

## Manual installer acceptance

After explicit approval for a Windows host, use `scripts/test-windows-install.ps1 -Installer <first.exe> -UpgradeInstaller <higher-version.exe>`. This is never run by CI. It refuses elevation and existing product, URL-scheme, PATH-owner, or shortcut registrations before installation. WebView2 must already be present.

The runner creates a unique folder under Documents/Codex and uses a synthetic `BERTH_HOME`, user directory, and loopback ports. It checks fresh-install consent, private API startup, a login task owned by `cli/berth.exe`, literal isolated task environment, an explicitly added PATH entry, manual higher-version upgrade, clean stop beyond the crash-retry interval, and supported uninstall. It compares the final task set and exact user PATH with their baselines, verifies personal preview pairing/identity files are unchanged, and retains synthetic keys and local evidence for inspection. It does not test failed-upgrade rollback without a separately prepared artifact and assertions.
